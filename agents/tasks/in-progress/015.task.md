# Task: Separate episode title and episode description inputs

## Context

The "Episode creator" screen currently has a single `input` labeled "What shall we explore tonight?" (placeholder/example value: "A gentle journey through the hidden life of the ocean"). This one field serves two purposes at the same time:

1. It is the **prompt/description** sent to the LLM pipeline that generates the video.
2. It is the **heading** shown in the UI (the label and, in some places, the displayed episode name).

This coupling causes problems: a descriptive prompt is often too long or too informal to work as a title, and a short title is not enough context for the LLM. The two concerns must be decoupled.

## Goal

Replace the single input with two separate fields:

- **Title**: a single-line `input` for the episode name. Used for display (UI headings, lists, saved episode name, and any output metadata).
- **Description**: a multi-line `textarea` for the detailed prompt/brief that is sent to the LLM pipeline.

## Requirements

### 1. Analyze the current implementation first

Before changing anything, locate and document:

- The component that renders the "Episode creator" form and the "What shall we explore tonight?" field.
- The state variable(s) bound to that input and every place they are read.
- The request/payload sent to the LLM pipeline (API endpoint, job queue, or function call) and the exact field it uses for the topic.
- Every place where the topic string is rendered as a heading, title, label, or saved name (list views, detail pages, file names, metadata, history, etc.).
- Any existing validation, default values, or tests that reference this field.

Summarize these findings briefly in the PR/commit description or a short notes file before implementing.

### 2. UI changes

- Add a **Title** `input` (single line) above the **Description** `textarea`.
- Keep the existing visual style (dark theme, rounded container, spacing) consistent with the current form.
- Title:
  - Label: "Title" (or equivalent).
  - Placeholder: a short example, e.g. "The Hidden Life of the Ocean".
  - Maximum length: define a reasonable limit (e.g. 100 characters) and show validation feedback when exceeded.
- Description:
  - Label: e.g. "Description" or "What should the episode cover?".
  - Placeholder: a longer example, e.g. "A gentle journey through the hidden life of the ocean…".
  - Multi-line, auto-growing or with a sensible default height and vertical resize.
  - Optional minimum/maximum length, consistent with what the LLM pipeline accepts.
- The page heading ("Episode creator") and subtitle stay as they are.

### 3. State and data flow

- Introduce separate state for `title` and `description` (do not reuse one variable for both).
- The LLM pipeline request must send **`description`** as the prompt/brief input.
- `title` must be sent as its own field (e.g. `title`) so it can be stored and displayed independently.
- If the pipeline currently only accepts one topic string, update its contract/schema (API, types, DTOs, validation) to accept both fields. Keep the change minimal and explicit.
- Wherever the UI previously displayed the topic as a heading or name, display `title` instead.

### 4. Validation

- Title is required (non-empty after trimming). Define whether description is required; default: required.
- Trim whitespace before submission.
- Disable the submit button while the form is invalid, or show inline errors.
- Do not submit when validation fails.

### 5. Backward compatibility

- If existing episodes or saved records contain only a single topic string, they must still render correctly. Fallback: use the old topic value as both `title` and `description`, or as `description` with a generic title, whichever matches existing data semantics. Document the choice.
- If there is a database or stored JSON, add a migration or a read-time fallback. Do not break existing records.

### 6. Tests

- Unit tests for validation (empty title, empty description, length limits, whitespace-only input).
- Test that the pipeline request payload contains both `title` and `description` with the correct values.
- Test that the heading/display uses `title`, not `description`.
- Test the fallback for legacy records (if applicable).
- Update or remove existing tests that assume a single topic field.

## Acceptance criteria

- [ ] The Episode creator shows two separate fields: a single-line Title input and a multi-line Description textarea.
- [ ] The LLM pipeline receives `description` as the prompt/brief and `title` as a separate value.
- [ ] Headings and episode names in the UI are derived from `title`, not from the description.
- [ ] Empty or whitespace-only title and description are rejected with clear feedback.
- [ ] Long text in the description wraps and scrolls correctly; the layout does not break on mobile widths.
- [ ] Existing episodes or saved data still display correctly (fallback implemented and documented).
- [ ] All existing and new tests pass.
- [ ] No unrelated refactoring is included in the change.
