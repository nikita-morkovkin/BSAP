# Task 009: Optional Ambient Mastering, Stem Exports, and Ambient Library API

## Objective

Refactor backend mastering so a missing ambient playlist does not fail a project. Always produce downloadable voice-only WAV/FLAC stems; when enabled ambient tracks exist, additionally produce duration-matched music-only WAV/FLAC stems and the mixed master WAV/FLAC. Add safe backend API operations for managing the shared ambient library.

## Related plan

- `/agents/tasks/BACKEND_PLAN.md`

## Implementation details

### 1. Output and state contracts

1. Extend `/backend/src/modules/state/schemas/state.schema.ts` output-file keys with optional voice and music WAV/FLAC paths. Retain `wav` and `flac` for the mixed master to avoid breaking current clients.
2. Extend `/backend/src/modules/projects/schemas/media-artifact.schema.ts`, its inferred type, and `/backend/src/modules/projects/media.service.ts` with stable artifact keys and MIME/filename mappings for voice and music stems.
3. Keep all optional output keys absent when files were not produced. Ensure start/retry paths clear stale output metadata.

### 2. Mastering pipeline

1. In `/backend/src/modules/audio/ffmpeg.service.ts`, continue building `output/voice_raw_full.wav` from assembled chapters and apply the configured voice mastering chain to a finalized voice-only WAV and FLAC.
2. Resolve enabled ambient tracks in explicit playlist order. Build the ambient cycle as today, then loop/trim/render an episode-length music-only WAV and FLAC aligned exactly with the finalized voice stem, including padding and fade behavior.
3. When at least one enabled track exists, mix the final voice and music stems at `ambientVolumeDb` and write the existing `master_final.wav` and `master_final.flac` artifacts. Preserve streaming downloads and ensure stem and mix durations match.
4. When there are no enabled tracks, skip ambient bed/mix rendering and complete successfully with voice outputs and metadata. Do not register mixed/music outputs in state.
5. Keep timestamps and timeline markers unchanged in meaning: they are based on chapter narration timing.
6. Ensure a remaster after playlist changes regenerates/clears relevant outputs so old mixes are not served as if current.

### 3. Ambient library API and persistence

1. Add an ambient library service/controller under the existing NestJS module conventions, backed by `AMBIENT_DIR` (defaulting to the current `assets/ambient` path).
2. Persist stable track IDs, display names, enabled state, and playlist order in a validated manifest written atomically. Existing WAV files not yet in the manifest should be safely adopted or handled through a documented migration path.
3. Implement:
   - `GET /api/ambient` to return ordered library records.
   - `POST /api/ambient` multipart upload for WAV files, with a bounded size, extension/content validation and FFprobe validation, generated safe filenames, and cleanup on failure.
   - `PATCH /api/ambient/:trackId` to change enabled state and optionally display name.
   - `PUT /api/ambient/order` to validate and persist the playlist order.
   - `DELETE /api/ambient/:trackId` to remove the file and manifest record safely.
4. Prevent path traversal and arbitrary file access; only IDs issued by the service can identify tracks. Make manifest changes atomic. Ensure a running mastering job uses a stable asset snapshot or otherwise cannot be corrupted by concurrent library edits.
5. Add the service/controller to the appropriate Nest module and use existing Zod validation/error conventions.

### 4. Tests and verification

1. Extend `/backend/src/modules/audio/tests/audio.integration.spec.ts` to verify:
   - Empty ambient library: project reaches `COMPLETED`, voice WAV/FLAC and metadata exist, and music/mixed artifacts are absent.
   - Enabled tracks: voice, music, and mixed WAV/FLAC artifacts exist, are valid, have matching durations, and mixed outputs remain stereo 44.1 kHz PCM WAV / FLAC.
   - Disabled tracks are excluded and playlist order is honored.
   - Retry/resume does not expose stale output state after a failed or changed mastering run.
2. Add API tests for upload validation, list order, enable/disable, reorder, delete, unsafe IDs/path handling, and persistence.
3. Update media download tests for MIME types, filenames, not-ready outputs, and streaming behavior for new artifact keys.
4. Run backend build and relevant unit tests. Run FFmpeg/BullMQ integration tests when FFmpeg, FFprobe, and Redis are available; state any skipped environmental prerequisites.

## Acceptance criteria

- Mastering no longer fails only because the ambient directory is empty or all tracks are disabled.
- Voice-only and existing metadata outputs are always available after successful mastering.
- With enabled ambient tracks, voice-only, music-only, and mixed outputs are generated and time-aligned.
- Existing `wav`/`flac` routes continue to refer to the mixed master when available.
- Ambient library API enforces safe uploads, deterministic order, enabled state, and safe deletion.
- Backend build and tests pass, with integration limitations reported accurately.
