# Task 011: Background Music Library Management and Project Track Selection

## Objective

Add backend and frontend support for uploading, listing, editing, replacing, and deleting background music, with per-project checkboxes controlling exactly which tracks enter the audio production pipeline.

## Current Implementation

- `n:\Projects\BSAP\backend\src\modules\audio\ffmpeg.service.ts` reads every WAV file from `AMBIENT_DIR` (default: `n:\Projects\BSAP\assets\ambient`), sorts by filename, and includes all of them in the ambient bed. An empty directory currently fails mastering.
- Projects persist validated state and profile data through `n:\Projects\BSAP\backend\src\modules\state\state-manager.service.ts`. There is no music catalog or project selection contract.
- The React application has create, monitor, and downloads views but no music management view.
- Docker already mounts `n:\Projects\BSAP\assets` read/write at `/app/assets`.

## Scope and Product Decisions

- Maintain a reusable global music library, but store inclusion choices per project. Library edits must never silently change an existing project's soundtrack.
- Initially accept WAV audio only, matching the existing pipeline. Validate actual audio with FFprobe, not only extensions or browser MIME types.
- Editing means changing a display name or replacing the source audio, not waveform editing. Replacement creates a new immutable file version while preserving the library track ID.
- New projects initially select all currently available tracks for compatibility. Users can clear every checkbox for narration-only production. Uploading another file must not automatically select it in already-saved projects or overwrite unsaved form choices.
- Preserve deterministic playback ordering through explicit ordered track IDs; checkbox order follows the displayed list. Drag-and-drop ordering, music generation, and video rendering are out of scope. The existing audio mix is the soundtrack used downstream for video creation.
- Task 012 depends on the project music snapshots defined here.

## Implementation Plan

### 1. Catalog, Storage, and Backward Compatibility

- Add a NestJS music module beneath `n:\Projects\BSAP\backend\src\modules\music` with separate controllers, services, Zod schemas, inferred types, DTOs, and utilities following repository rules.
- Store a validated catalog beneath the configured ambient root. Track records include stable ID, display name, original filename, immutable version, internal relative file path, duration, size, and timestamps. Never expose absolute storage paths.
- Serialize catalog mutations and use temporary files plus atomic publication. Clean up interrupted uploads and replacements without publishing incomplete records. Define a recovery/reconciliation strategy for interrupted catalog updates.
- Import existing WAV files once with deterministic ordering and stable persisted IDs. Skip catalog files and temporary files. Report invalid or unreadable audio instead of failing the entire listing.
- Make `AMBIENT_DIR` resolution shared between library and pipeline. Preserve native Windows and Docker operation; document upload size and duration limits in configuration examples.
- Add optional migration-compatible project music state: ordered selected IDs, immutable project-local source snapshots and metadata, and a selection revision. Extend strict schemas and frontend types together.
- Resolve a legacy project's missing selection once to the current valid library in the old filename order and persist it before mastering. Distinguish missing selection from an explicitly empty array. Do not invalidate an already-completed legacy export solely on read.

### 2. Backend API Contract

- `GET /api/music`: list library metadata and availability.
- `POST /api/music`: upload a WAV file with an optional display name using NestJS's existing Express platform integration; stream uploads to bounded temporary disk storage rather than buffering whole files.
- `PATCH /api/music/:trackId`: update a validated display name.
- `PUT /api/music/:trackId/file`: validate and publish a replacement source version.
- `DELETE /api/music/:trackId`: remove the library entry/source without removing snapshots already owned by projects. Coordinate deletion/replacement with concurrent snapshot creation; no dangling project references may be committed.
- Extend project creation to accept an ordered, unique selection of track IDs, including `[]`. Snapshot and validate selected sources before queueing project work.
- `PUT /api/projects/:id/music`: atomically replace the project's ordered selection, return current state, and invalidate derived mix artifacts. Reject stale revision writes and active/queued production conflicts with HTTP 409. An unchanged selection is a no-op.
- `POST /api/projects/:id/remaster`: explicitly queue a new mix from existing assembled narration, using the existing recoverable mastering queue. Do not regenerate scripts or TTS for a music-only change.
- Use HTTP 400 for invalid metadata/IDs, 413 for oversized uploads, 415 for unsupported content, 404 for absent resources, and 409 for lifecycle/version conflicts. Return actionable validation details.
- Validate IDs and resolve real paths within approved roots, including symlink checks. Generate storage filenames server-side; never accept filesystem paths from the browser. Clean temporary files on rejection, disconnect, and probe failure.

### 3. Project Snapshots and Pipeline Integration

- Store copies of selected source versions under each project's music directory with safe generated filenames and metadata. Retain source identity/version and selection revision for reproducible rendering and Task 012 downloads.
- Library rename, replacement, or deletion affects future selection only. Existing project snapshots remain usable after restart or library deletion. A missing/corrupt selected snapshot must produce a clear error rather than silently substituting another track.
- Update `buildAmbientBed()` to read only the committed project snapshot list in its stored order, not scan the global directory. Keep speed, volume, crossfade, and seamless-loop behavior.
- Add a zero-track branch: skip ambient generation and mixing while retaining voice mastering, padding, fade-out, final formats, and metadata exports.
- Make mastering completion revision-aware so an old worker cannot publish artifacts for a superseded selection. Guard selection updates against queued jobs as well as active workers using the project's existing locking/queue conventions.
- Invalidate ambient cycles, mixed masters, music manifests, and bundle artifacts after selection changes; retain chapter/chunk audio and valid narration-only artifacts. Extend resume checks to recognize missing/stale derived outputs.
- Ensure project deletion removes its music snapshots and temporary artifacts but never the shared library.

### 4. Frontend Library and Checkbox Selection

- Add a Music Library navigation view connected through `n:\Projects\BSAP\frontend\src\App.tsx` and the existing navigation/store types. Provide upload, metadata edit, replacement, and confirmed deletion controls.
- Show name, original filename, duration, size, availability, and per-action progress/errors. Explain that deleting a library entry does not delete existing project copies.
- Add a reusable checkbox selector to the create form and project detail view. Each checkbox explicitly says that the track is included in production. Provide Select all, Clear all, selected count, and a clear narration-only empty state.
- Keep selection changes local until Save/Create succeeds; show unsaved changes, preserve them across refetches, and roll back/report failed saves. Reconcile removed library entries without silently changing saved project snapshots.
- In project details, distinguish the saved soundtrack from current library versions. Show when a selected snapshot's library entry is gone; offer explicit removal or replacement rather than silently deselecting it.
- Disable saving/remastering while production is queued/active and explain why. After a saved change, mark the mix as needing a rebuild and provide an explicit Rebuild mix action.
- Add domain API methods in `n:\Projects\BSAP\frontend\src\api\music.api.ts`, register them in the API aggregator, and use dedicated TanStack Query hooks/mutations with targeted invalidation. Keep server state out of Zustand.
- Reuse installed UI components or accessible native checkboxes; provide labels, keyboard operation, focus handling, and non-color-only status feedback. Keep components under the repository's 200-line limit.
